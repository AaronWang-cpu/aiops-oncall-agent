## 2. 项目背景与当前重点

用户希望通过改进智能 Oncall Agent 项目提升工程能力，用于申请大厂实习。

长期方向曾讨论为：

1. 建立合理的评测集。
2. 建立 trace 架构，记录诊断过程。
3. 根据量化信息改进 Agent 的 harness 设计。

**当前优先事项是把诊断架构和实际推理能力做好，暂不围绕评测和 trace 设计方案。** 不能再以“评测可复现”“避免 trace 污染”等理由，将需要 LLM 的能力替换成规则壳。

当前目标是从简单日志采集流程，演进为综合日志、指标、变更与项目知识的假设驱动诊断闭环。

工作目录中的 Git 仓库为 `agent_py-release-2026-09-08/`，并非外层同名工作区目录。本文创建前检查到当前分支为 `feature/multi-source-evidence-architecture`，工作区干净。后续会话应重新检查 Git 状态，不把此快照当成永久状态。

### 3.3 必须如实理解的实现状态

当前流程大致为：

```text
planner → executor → executor（剩余步骤）→ evidence_reasoning
                                               ↓
                               追加查询 / report
```

- 工具实际按 `plan_index` **串行执行**。一次生成三步计划不是并行执行。
- Planner 使用 LLM 生成日志查询计划；指标和变更步骤主要由程序附加。
- 当前 QueryMetric 并没有完整实现“LLM 主导选择指标”的目标设计，而是使用配置指标构造步骤。
- `evidence_reasoning` 当前不调用 LLM，不综合日志和指标进行因果判断。
- 当前规则主要是：变更未命中时，扩查二级依赖；否则结束。固定上限为 2 轮。
- 命中变更不等于找到根因，“没有追加查询”也不等于证据充分。
- 指标和变更仍为模拟数据；Mock 接通不等于接入真实观测系统。
- 现有图状态没有完整的假设生命周期、反证、因果链和结构化停止原因。

此前静态审查还指出：状态中的工具摘要和报告上下文存在截断；前端节点过滤、变更证据类型契约、案例根因字段和超时终态同步可能需要对齐。这些是实现时应核对的兼容点，不应借此无限扩大本次改造范围。

#### 已确认的 Mock 事故数据一致性与入口隔离

用户经整体审阅后确认：一个模拟事故对应一份固定数据快照，三个模拟工具只查询这份快照。本节补充原路线 A 的开发方案，不压缩日志、不优先适配真实 CLS 返回结构，也不将模拟数据冒充生产事实。

| 事项 | 已确认方案 |
|---|---|
| 场景组织 | 用一份独立的模拟事故数据文件保存告警、日志、指标序列和变更事件，统一服务、实例及时间线 |
| 时间基准 | 在任务开始时固定场景时间基准；后续查询只按条件筛选，不随查询窗口重新制造指标峰值或移动变更时间 |
| 查询行为 | 日志、指标和变更分别按各自参数过滤已有数据；未知数据返回空结果或明确能力缺口，不临时编造 |
| 开发入口 | 显式选择 Mock 模式并固定场景，通过依赖注入提供模拟工具，保留现有工具接口；真实模式继续使用真实 MCP，不因失败自动回退 Mock |
| 推理输入 | 只提供告警、项目知识及实际查询结果，不注入预设根因、期望结论、评分信息或场景答案提示 |
| 展示边界 | 在任务与报告层明确标记“模拟场景”，不在四字段业务证据记录中重新增加 `source` 等已删除字段 |

本期先准备覆盖正常闭环的少量独立场景数据，允许包含无关日志、无关变更和缺失证据。可以参考实际机制人工构造数据，但不从已有评测标准答案反推项目知识或假设模板，不改动原有评测集，也不因本节审批运行新评测。模拟项目说明须明确其模拟性质，不伪装成实际项目已核实知识。

模拟场景内仍允许按既有确认标准进入根因确认分支，但不表述为真实生产事故已经确认。数据一致不等于证据充分；缺失因果环节或尚存主要竞争解释时，仍须保持未确认。

**已确认的取舍：** 需要补充独立场景数据，不能完全沿用当前按服务/指标哈希、在每个查询窗口中段制造异常峰值的实现。后续补查必须检验同一个事故，而不是每次查询重新生成一个事故。当前代码和历史实现说明保留为现状，不因此声称固定快照及入口隔离已实现。具体数据文件路径、显式模式选择方式及工具适配由工程规格对齐既有配置和接口；不另建后端应用或 MCP 平台。

### 4.4 调查预算

用户明确选择 B 方案：

| 项目 | 上限 |
|---|---:|
| 调查轮数 | 5 轮 |
| 工具调用 | 20 次 |
| 总时长 | 8 分钟 |

一轮包含一次实际启动的工具执行批次，以及围绕该批结果的假设生成、评估和有限调整。已确认以本批第一个工具调用实际发起为计数点，`rounds_used` 加 1，不等到分析成功才计轮；首轮也计入，失败不返还。第 5 轮禁止启动新批次，但保留时间允许范围内的结果分析和有限内部调整，详见第 8.2 节。预算是保护上限，不是必须用满；确认根因后提前结束。

后续确认增加内部执行保护：两种不经过工具执行的内部往返共用 2 次额度，使用程序控制状态 `internal_steps_used` 计数，详见第 8.2 节。这不是两个节点合计只能调用两次，也不是连续无实质进展检测；5 轮、20 次、8 分钟上限保持不变。内部预算触顶且无法转入有效工具执行时，可按 `budget_exhausted` 收尾。

## 5. 讨论收敛的诊断原则

### 5.1 不使用数值置信度驱动初版流程

后续讨论撤回了“将 LLM 判决映射为固定分数，再加权得到置信度”的方案。

初版不需要数值 `confidence`，尤其不能把未经校准的 0.7 解释成真实根因概率。下一轮查询优先级可以依据证据缺口及区分候选的价值判断，不要求概率计算。

### 5.2 假设状态与整体结束决策分开

**已明确确认：** 每个假设只使用一个综合状态字段 `hypothesis_status`，取值为 `pending / investigating / blocked / supported / contradicted / unresolved`。不再采用旧的三值 `verdict`，也不另加 `investigation_status` 或独立生命周期字段。

讨论过程曾暂时去掉 `unresolved`，用户最新确认已将其恢复；后续以六值方案为准。原来的 `insufficient` 无法区分尚未验证、正在验证、验证受阻和结束后仍无结论，因此不再作为字段取值。

各状态的语义整理如下；整体停止时的收尾转换见第 5.5 节。用户已确认调查中依据新证据或阻碍解除重开旧判断，及整体终态后不再修改本次调查的规则，见第 8.4 节更新与兼容方案；不另建独立生命周期状态机。

| 值 | 含义 |
|---|---|
| `pending` | 当前解释尚待评估或验证；新增及实质性细化后暂时初始化为此状态，不代表此前从未调查 |
| `investigating` | 正在验证，现有证据尚不足以支持或反驳，仍在推进查询或证据分析 |
| `blocked` | 关键验证受阻，当前没有可执行的有效替代路径；需说明阻碍及恢复条件 |
| `supported` | 已有证据支持假设的必要因果环节，没有未解释的关键反证 |
| `contradicted` | 可靠证据否定假设成立所必需的前提或环节 |
| `unresolved` | 本次不再继续追查该假设，但证据仍不足以支持或反驳；需说明结束原因和剩余缺口 |

**已明确确认：** `blocked` 表示整体调查仍在进行，但该假设的关键验证当前无法推进；`unresolved` 表示本次已结束对该假设的追查，仍无支持或反驳结论。整体停止时，剩余 `pending / investigating / blocked` 统一转为 `unresolved`，原进展、阻碍和缺口通过 `assessment` 与 `gaps` 保留。此前“预算耗尽后保持 investigating”的建议已被替代。

判定标准需要进入 prompt，LLM 输出证据引用和简短理由；程序校验结构和引用，不能声称仅靠校验就保证语义正确。

重要限制：

- 低支持度不等于被反驳；没查到不等于不存在。
- 重复症状日志不等于多份独立佐证。
- 如果假设本身的必要因果环节仍缺证据，不能标为 `supported`；应根据调查进展使用相应未决状态，并说明缺口。
- 一个假设得到支持，不意味着整个事故已充分解释。
- 单次工具失败不等于假设被反驳；若仍有有效替代路径，也不应仅凭该次失败判为 `blocked`。
- 新增或实质性细化后由程序暂时初始化为 `pending`，随后立即使用已有证据重新评估，不强制额外查询。这替代此前“不强制先进入 pending”的建议，具体契约见第 8.2 节。
- 假设状态与事故级根因确认、整体停止原因分开；不能因为预算结束就把假设标为 `contradicted`，也不能将 `supported` 自动升级为事故根因已确认。

### 5.3 根因确认标准

最近讨论提出的简化标准为：

1. 原因具体：不能只说“数据库问题”或“发布问题”。
2. 因果链有证据：能说明该原因如何导致本次告警，不只是在时间上接近。
3. 没有未解决的关键反证或主要竞争解释。

例如，“故障前发布过”只能提出假设；“发布降低连接上限、受影响实例连接满载并出现等待超时、对象和时间一致”才有更具体的因果支持。

不强制必须有回滚实验，也不强制凑齐日志、指标、变更三种证据。关键是证据能否支撑对应因果环节。

### 5.4 多假设与后续查询

- 多个假设得到支持，可能是同一因果链不同位置，也可能是共存因素，不能自动当成多个独立根因。
- 竞争解释和因果链关系应在 Evidence Reasoning 中处理，不到 Report 才首次推理。
- 后续查询优先解决会改变根因判断或处置建议的不确定性。
- 一个查询可以验证或区分多个假设，不为每条假设固定分配调用。
- 不机械只追查排名第一者，也不每轮全量追查所有假设。
- 不每轮重新生成假设；优先更新、细化或依据证据排除已有假设。本期不执行合并重复解释，也不将合并能力转移到其他节点。
- 新事实不能由当前假设解释、主要候选被排除等情况下，允许新增假设。

### 5.5 停止调查与报告

当前事故级 `stop_reason` 仅保留：已确认具体根因、达到预算、关键数据不可用，具体枚举及边界见第 5.10 节。不再将“没有可执行且有价值的补查”“连续两轮无实质进展”“执行错误”作为独立停止原因；本期不实现连续无进展检测。任务自身的异常、超时和取消语义不由这一枚举替代。

停止不等于确认。Report 应接收完整诊断状态，包括主要候选、已排除方向、关键证据、缺口及停止原因；Top-K 最多是展示重点，不能作为丢弃其他判断的边界。

#### 已确认的整体收尾规则

**整体调查确定结束时，所有仍未得到支持或反驳的假设统一收敛为 `unresolved`。** 最终报告中的假设状态只保留 `supported / contradicted / unresolved`；`pending / investigating / blocked` 用于表达调查过程中的进展。这里的整体停止不是一轮结束，也不是暂时等待工具结果。

| 收尾前状态 | 收尾后状态 | 必须保留的信息 |
|---|---|---|
| `pending` | `unresolved` | 当前解释尚待评估或验证，以及为何结束；若是细化后待评估，不能误写为此前从未调查 |
| `investigating` | `unresolved` | 已验证到哪一步、剩余缺口及结束原因 |
| `blocked` | `unresolved` | 原有阻碍、恢复验证所需条件及本次结束原因 |
| `supported` | 保持 `supported` | 支持理由、关键证据及证明边界 |
| `contradicted` | 保持 `contradicted` | 否定必要前提或因果环节的证据 |
| `unresolved` | 保持 `unresolved` | 已有结束理由和缺口，不被通用收尾说明覆盖 |

上述转换基于最后一次有效证据判断，只表达结束追查，不生成或修改因果结论。假设也可以在整体结束前进入 `unresolved`，前提是已明确决定本次不再追查该方向；不能仅因本轮未被选中就转换。

#### 保留不同假设的未解决原因

统一状态不等于抹平过程差异，不增加新的假设字段：

- 调查级状态记录“整体为什么结束”，仅采用第 5.10 节确定的根因已确认、预算耗尽或关键数据不可用。
- `assessment` 保留“该假设为什么仍无结论”，包括此前是否验证、已有进展、关键阻碍及相应结束理由；不能一律替换为“调查结束”。
- `gaps` 保留尚未回答的关键问题；验证受阻时，在 `assessment` 中保留恢复条件，不能因状态转换而清空缺口或证据关联。

例如，同样因工具调用预算耗尽而结束，以下仅为表达示例，不代表真实事故事实：

| 原状态 | 收尾后的 `assessment` 示例 |
|---|---|
| `pending` | 本假设尚未开展针对性验证；工具调用预算已耗尽，本次结束追查，不能支持或排除。 |
| `investigating` | 已发现连接等待增加，但尚未验证实际生效的连接池上限；工具调用预算已耗尽，无法完成关键机制验证。 |
| `blocked` | 验证需要实例实际生效配置，现有工具无法获取且无有效替代路径；本次调查因预算耗尽结束，继续验证需补充配置快照。 |

#### 找到根因不等于反驳其他假设

- 某个假设已获支持，且综合全部证据满足事故级根因确认标准时，可以提前结束调查。
- 其他假设只有必要前提或因果环节被可靠证据否定，才能判为 `contradicted`；不能因为找到一个解释，就自动排除其余解释。
- 同一因果链中的其他已获支持假设保持 `supported`，但不自动视为多个独立根因。
- 尚未验证、也未被反驳的其他假设转为 `unresolved`，说明本次不再追查的原因。
- 若某个未决假设仍是会实质改变根因判断的主要竞争解释，就不能宣称具体根因已经确认。应继续调查；若受预算等限制必须停止，事故级结论也必须保留不确定性。

#### 收尾顺序与职责边界

1. 在预算和调用条件允许时，分析已返回但尚未分析的证据。
2. 更新假设的证据判断，并确定事故级结论及整体停止原因。
3. 对剩余 `pending / investigating / blocked` 执行统一的 `unresolved` 收尾转换，保留各自理由和缺口。
4. Report 表达最终状态、证据、过程差异与局限，不首次推理或升级结论。

证据推理决定假设能否进入 `supported` 或 `contradicted`；程序收尾只转换未决状态，不生成新的因果解释。若已触及硬截止时间或模型调用失败，不得为最后分析自动延长预算：保留最后一次有效且一致的判断，完成可执行的状态收尾，并明确标记存在尚未分析的结果，不能声称这些结果已经纳入结论。分阶段时间及报告兜底见第 8.2 节；旧判断与新状态不一致时不能盲目沿用，具体一致性保存及异常恢复机制仍待工程设计。

### 5.6 每个假设的字段与下游使用

#### 已确认的六字段方案

用户确认在此前七字段建议中删除 `scope`，每个假设只保留以下六个顶层字段，并认可原因与缺口说明。不另设 `verdict`、`investigation_status`、数值置信度或独立生命周期字段。

| 字段 | 类型 | 内容与用途 |
|---|---|---|
| `hypothesis_id` | 字符串 | 稳定、唯一的假设 ID，用于查询关联、假设更新和关系引用 |
| `statement` | 字符串 | 具体原因解释及必要因果机制，说明究竟验证什么，不仅给出故障类别 |
| `hypothesis_status` | 字符串枚举 | 第 5.2 节确认的六种状态之一 |
| `assessment` | 字符串 | 当前判断和状态的简短理由，包括为何支持、反驳、继续调查、受阻或结束后仍无结论 |
| `evidence_links` | 对象列表 | 与假设相关的证据引用、证据作用和解释 |
| `gaps` | 对象列表 | 尚未解决且会影响判断的关键问题及其重要性 |

**列表结构澄清：** `evidence_links` 和 `gaps` 的外层都是列表，列表内每一项是一个字典（JSON 对象）；此前展示的单个字典只是其中一项，不是整个字段。没有相关条目时使用空列表 `[]`。

删除 `scope` 不等于忽略服务、实例或时间范围。建议在 `statement` 中写明区分该假设所必需的对象信息，查询范围结合调查级告警上下文、拓扑和现场证据构建，不再给假设新增范围字段。

#### 内容边界与嵌套结构

以下为六字段的内容细化说明；证据引用粒度已确认只使用整份结果引用，不设条目定位字段。字段写入职责及新增、细化后的重置规则见第 8.2 节；用户经整体审阅后确认以下证据关联、缺口嵌套字段及 `supports / contradicts / context` 枚举，更新与兼容见第 8.4 节。

- `statement` 将原因和机制合在一段简短解释中，不再拆成多个重复文本字段。尚未证实的原因明确作为假设表达，不能写成既定事实。
- `assessment` 解释当前为什么作出这一判断，而不是重复 `statement`；统一承担状态理由，不另设多个原因字段。受阻时说明阻碍与恢复条件，未解决而结束时说明结束理由。
- `evidence_links` 每项包含 `evidence_id / relation / explanation`。`evidence_id` 引用整份工具结果，不增加 `locator` 或单条日志、指标点、事件的引用 ID。`relation` 为 `supports / contradicts / context`，分别表示支持、反对或仅提供相关背景。`explanation` 说明证据涉及哪个因果环节及其证明边界。
- 单条证据的 `supports` 不等于假设整体的 `supported`。重复症状不等于独立佐证；项目知识不是现场证据，不能混用引用。
- `gaps` 每项包含 `question / why_it_matters`，分别说明待回答的问题及其为何影响判断。不预写所有工具参数或大量验证分支，一个查询可以解决多个假设的缺口。
- 当前 `gaps` 只保留未解决问题；已解决问题的依据进入 `assessment` 和 `evidence_links`，过程留在共享查询记录中。具体历史保存方式仍待工程设计。

以下仅为结构示例，不代表真实事故证据，也不是根据评测答案生成的模板：

```json
{
  "hypothesis_id": "H1",
  "statement": "payment-service 本次发布可能降低了连接池上限，导致请求等待连接并超时，进而触发接口延迟告警。",
  "hypothesis_status": "investigating",
  "assessment": "连接等待增加与该解释一致，但尚无实际生效配置的证据，不能确认上限降低。",
  "evidence_links": [
    {
      "evidence_id": "E12",
      "relation": "supports",
      "explanation": "连接等待增加支持连接池容量不足这一环节，但不能证明配置上限发生变化。"
    }
  ],
  "gaps": [
    {
      "question": "发布前后，受影响实例的连接池上限是否实际降低？",
      "why_it_matters": "用于区分配置变更导致容量下降与请求增长导致原有容量不足。"
    }
  ]
}
```

#### 共享信息与下游消费建议

讨论方向是：假设保存“怀疑什么、目前怎么看、还缺什么”，调查级共享状态保存“查过什么、下一步查什么、为什么停止”。以下分工是建议，不代表已批准共享状态的完整 schema：

| 信息 | 建议存放位置 | 理由 |
|---|---|---|
| 完整工具返回内容 | 共享证据集合，四字段方案见第 5.7 节 | 多个假设可引用同一份结果，不重复复制原文 |
| 工具参数、执行终态、结果关联和失败原因 | 执行后写入查询记录，通过 `hypothesis_ids` 关联假设，见第 5.8 节 | 一个查询可以验证或区分多个假设；暂不重试 |
| 本轮验证重点及查询优先级 | 本轮计划 | 优先级是动态的相对选择，不是假设固有属性 |
| 假设之间的竞争、因果关系 | 调查级关系集合，两种关系与五字段见第 5.9 节 | 避免在多个假设中重复维护同一关系 |
| 假设修改历史 | 轻量更新记录 | 假设保留最新判断，历史保存方式另行确定；本期不做假设合并 |
| 事故级根因确认、预算、整体停止原因 | 四字段事故级结论见第 5.10 节；预算由控制状态管理 | 不与单个假设的状态混淆 |

| 下游步骤 | 需要读取的信息 | 目的 |
|---|---|---|
| 生成或更新假设 | 已有假设、完整相关证据、缺口、查询历史及假设关系 | 判断应细化旧假设、排除旧方向，还是新增解释 |
| 生成工具调用 | 假设解释、关键缺口、证据判断、查询历史、工具能力、调查范围与预算 | 决定查什么、为什么查、是否重复及能否区分候选 |
| 生成报告 | 全部假设的收尾状态、理由、证据引用、缺口及调查级结论与停止原因 | 按 `supported / contradicted / unresolved` 表达最终判断，并通过理由区分未验证、验证未完成和曾受阻等过程差异 |

这些字段不是日志压缩方案，也不能代替查询历史或完整证据。现阶段仍按已确认要求让推理消费完整相关 Mock 数据；Report 不得仅凭状态标签升级结论或编造新根因。

### 5.7 共享证据集合与引用粒度

#### 已确认的字段与引用选择

用户明确删除此前共享证据记录建议中的 `source`、`coverage` 字段，只保留以下四个业务字段。**假设只使用整份结果引用，不采用条目级引用，不增加 `locator`。**

| 字段 | 内容与用途 |
|---|---|
| `evidence_id` | 稳定、唯一的证据 ID，供假设和报告引用整份结果 |
| `query_id` | 对应工具执行记录的 ID，用于关联实际工具调用上下文 |
| `kind` | 事故工具证据类别使用 `log / metric / change`，与现有单数形式对齐，共享契约补充 `change`；存储中的告警、知识引用与现场工具证据分开 |
| `data` | 本次工具实际返回的完整业务内容，不以摘要替代 |

这确定的是共享证据记录的业务结构，不表示已新增数据库表，也不批准具体持久化方案。实际存储仍须遵守任务归属及用户权限隔离，不能因简化业务字段而丢失权限边界。

#### 组织方式与引用语义

沿用本轮讨论的组织方向：一次实际工具调用返回的结果作为一份证据记录；“共享”限定于同一次调查中各假设和节点复用，不是跨用户或跨事故混用。

```text
Q1：一次日志查询   -> E1：该次返回的完整日志列表及返回元信息
Q2：一次指标查询   -> E2：该次返回的完整指标结果
Q3：一次变更查询   -> E3：该次返回的完整变更或事件结果
```

- 多个假设可以引用同一 `evidence_id`，不为每个假设复制原始结果。
- 整份结果引用不表示其中每个条目都支持该假设。`explanation` 仍需说明有关发现、对应因果环节及证明边界，但不另建条目定位机制。
- 结果中有一部分支持证据，不等于整条假设可以标为 `supported`；仍须满足必要因果环节的判定标准。
- 工具名称、实际参数、执行终态及失败原因保留在查询记录中，通过 `query_id` 关联；七字段与执行后记录的约定见第 5.8 节。运行时间信息如何关联任务执行层仍待工程设计，不在查询记录中新增重试字段。
- 已保存的结果建议不被后续查询覆盖，新结果使用新证据 ID；假设解释可以更新，但不能反向改写原始返回内容。

#### 完整结果与异常边界

删除 `source`、`coverage` 是简化证据记录字段，不要求删除工具原本返回的业务字段或元信息，也不另建同义字段替代它们。

- `data` 保留实际返回的日志、指标、事件及工具已有的相关返回元信息。当前直接使用 Mock 数据，不先适配真实 CLS 返回结构，不压缩或静默截断。
- “完整保存本次返回”不等于“查询范围内全部数据均已获取”。工具若原本返回分页、截断或部分结果提示，应随原始结果保留；没有相关信息时，不得声称覆盖完整。
- 完整业务内容不包括鉴权头或凭据；继续遵守安全脱敏要求。项目知识也不作为本次事故的工具证据混入。

空结果与无业务数据的失败处理已在第 5.8 节明确；部分返回的具体处理仍需结合工具契约细化，不增加查询状态枚举或重试标识：

| 情况 | 建议处理 |
|---|---|
| 成功但业务结果为空 | 保存该次完整返回及查询关联；空结果不等于假设被反驳 |
| 调用失败且无业务数据 | 查询记录保留失败原因，不伪造正常证据 |
| 获得部分数据后失败或明确返回部分结果 | 保存已获得的数据及原有提示，查询记录说明失败或部分返回，不包装成完整成功 |

推理节点读取证据时应同时获得关联查询的必要上下文，而不是只收到无法解引用的 ID；Report 也不能把假设的 `explanation` 当成原始证据。结果已保存但尚未经过分析时，需在调查级记录中区分，不能声称已有结论考虑了全部已存结果。

### 5.8 查询记录

#### 已确认的定位与字段

**查询记录是工具调用执行结束后的记录，不承担计划管理或执行中状态管理。** 用户明确要求 `status` 仅保留 `succeeded / failed`，删除 `retry_of`，暂不考虑工具调用重试，并在执行后记录。

在上一版方案基础上，查询记录收敛为以下七个业务字段：

| 字段 | 类型 | 内容与用途 |
|---|---|---|
| `query_id` | 字符串 | 本次实际工具调用的唯一 ID，供共享证据关联 |
| `hypothesis_ids` | 字符串列表 | 关联的假设 ID；一次查询可服务多个假设，尚无假设的首轮采集可为空列表 |
| `question` | 字符串 | 本次查询要回答的问题及其判别价值，不只重复工具名称 |
| `tool_name` | 字符串 | 实际调用的工具名称 |
| `arguments` | 对象 | 实际使用的调用参数，不只是自然语言查询意图 |
| `status` | 字符串枚举 | 仅 `succeeded / failed`，表达执行结果而非假设判断 |
| `status_reason` | 字符串或 `null` | 执行结果的必要说明，尤其是失败原因；正常成功时可为 `null` |

不保留 `retry_of`，不增加 `pending / running / skipped / cancelled` 等查询状态。共享证据已通过 `query_id` 关联调用，不重复维护查询记录中的 `evidence_ids` 列表。

#### 写入时机与执行语义

- 工具正常返回或以错误结束后，写入查询记录；未执行的计划不进入查询记录。
- 待执行、执行中、跳过等情况由计划或任务执行层管理，不能为了表达它们扩展查询记录状态。
- 正常返回空业务结果仍为 `succeeded`，不能把无命中当作调用失败或假设反证。
- 超时、接口报错等执行错误记为 `failed`，通过 `status_reason` 保留原因；失败且没有业务数据时，不伪造正常证据。
- 完整业务返回保存在共享证据集合中，以 `query_id` 关联。`status_reason` 不复制完整返回，也不保存根因判断。
- 获得部分数据的处理需结合工具契约判断，并保留原有提示；不新增 `partial` 状态，不把执行失败包装成正常成功。

执行后记录不等于仅靠已写入的查询条数控制预算：任务执行层仍需在实际发起调用时计数，失败调用也占用预算；未执行的计划不占用实际调用次数。具体超时、取消、执行时间及进程异常时的记录恢复方式仍待工程设计，不因此增加业务字段或假定现有实现已经满足要求。

#### 暂不重试与补查边界

- 本期工具调用失败后如实记录，不自动重复调用，不建立重试关联。这替代此前“可恢复工具错误最多重试一次”的讨论方向。
- 实现前需核对执行层是否存在隐式工具重试，不能只删除字段却仍在内部重复调用。
- 基于证据缺口修改范围、条件或更换工具的有依据补查，是新的查询；不能只换 ID 就将同一失败调用的重试伪装成补查。
- 再次读取已有结果应复用共享证据，不产生新的工具调用记录。
- 本约定针对调查工具调用，不自动改变模型无效输出修正或后台任务恢复等其他机制；其边界仍按各自工程规格明确。

#### 下游使用边界

查询记录回答“为什么查、怎么查、执行得怎样”，共享证据回答“实际返回什么”，假设回答“如何解释、还缺什么”。`question` 可以简短说明查询区分哪些解释，但不预写无依据的数值阈值或固定因果判决。证据对假设的支持、反对关系仍保存在假设的 `evidence_links` 与 `assessment` 中，避免两处结论不一致。

### 5.9 调查级假设关系集合

#### 两种关系与五个字段

用户确认将“两种关系和五个字段”的方案记录为后续设计依据。关系集合是同一次调查状态中的对象列表，不在每个假设里重复保存关系，不为此另建复杂图系统；具体持久化和更新实现仍待工程设计。

| `relation_type` | 含义 | 方向与调查用途 |
|---|---|---|
| `causal_link` | 两个假设可能位于同一因果链，存在上游原因到下游结果的联系 | 有方向，`from` 为上游、`to` 为下游；检查连接机制，避免把下游表现直接当作最终根因 |
| `competing` | 两个假设对同一关键现象提出不同解释，需要区分各自的解释作用 | 无方向，仅保存一条，不保存反向重复记录；优先寻找区分性证据 |

第一版不增加“相关”“共同出现”“相似”等宽泛关系类型。

| 字段 | 类型 | 内容与用途 |
|---|---|---|
| `from_hypothesis_id` | 字符串 | 关系一端的假设 ID；因果关系中表示上游 |
| `to_hypothesis_id` | 字符串 | 关系另一端的假设 ID；因果关系中表示下游 |
| `relation_type` | 字符串枚举 | 仅 `causal_link / competing` |
| `explanation` | 字符串 | 建立关系的原因、当前依据及尚未解决的不确定性 |
| `evidence_ids` | 字符串列表 | 支撑关系判断的整份证据 ID，可以为空列表 |

外层为列表，每一项是一条关系对象。暂不增加关系 ID、数值置信度或独立关系状态机；`evidence_ids` 只引用整份工具结果，不引入条目定位。

以下是结构示例，不代表真实事故结论：

```json
[
  {
    "from_hypothesis_id": "H1",
    "to_hypothesis_id": "H3",
    "relation_type": "competing",
    "explanation": "连接池上限降低与请求量增长都能解释连接等待增加，需要比较实际配置变化与请求量变化；目前不能排除两者共同作用。",
    "evidence_ids": []
  }
]
```

#### 关系语义与证据边界

- **记录关系不等于关系已被证实。** 允许记录待验证的联系以指导补查，`explanation` 必须说明是推测还是已有证据支持，并指出关键缺口。
- **竞争不等于互斥。** 例如配置降低容量与请求增长可能同时发生；一个假设成立，不能据此自动反驳另一个。
- 两端假设各自为 `supported`，不自动证明中间的因果连接成立；仍需证据支持对象、时间和机制上的联系。
- `evidence_ids` 非空也不等于关系成立。时间接近等证据可能仅支持进一步调查，不能包装成完整因果证明。
- 假设证据解释“为什么认为某个解释成立”，关系证据解释“为什么认为两个解释之间存在这种联系”，两者作用不同，可以引用同一份证据。
- 关系中的关键未决问题应落入相关假设的 `gaps`，避免只在关系说明中提出却未安排调查。
- 不根据缺少关系记录推断假设彼此独立；没有记录不等于不存在联系。

初版不靠 `relation_type` 自动判断因果成立，而由 Evidence Reasoning 结合关系说明、假设判断及原始证据综合分析。Report 不得仅根据关系标签拼接确定的因果链，也不能把多个已获支持的上下游假设自动当作多个独立根因。

#### 下游使用与维护边界

| 使用方 | 主要用途 |
|---|---|
| 生成或更新假设 | 区分补充已有因果链与提出竞争解释，减少重复假设 |
| 生成工具调用 | 对因果关系补查连接机制，对竞争关系寻找区分性证据；一个查询可服务多个假设 |
| 生成报告 | 组织有证据的因果链，区分原因与下游表现，如实表达未解决的主要竞争解释 |

关系集合不替代 `hypothesis_status`，不自动支持或排除假设。用户最新确认本期不合并重复解释，不增加“重复关系”或合并历史。关系由 `assess_hypotheses` 维护，假设解释变化后必须重新检查相关关系，不能只因 ID 未变而沿用旧判断，见第 8.2 节。具体修订、删除和中间状态保存方式仍待工程实现统一，不将当前方案视为已完成的运行能力。

### 5.10 事故级结论与整体停止原因

#### 四字段方案

事故级结论回答“具体根因是否确认、确认了什么、为什么停止”。用户明确删除此前建议的 `related_hypothesis_ids / evidence_ids / limitations`，采用以下四字段方案，不增加同义替代字段或数值置信度：

| 字段 | 类型 | 内容与用途 |
|---|---|---|
| `conclusion_status` | 字符串枚举 | `confirmed / unconfirmed`，表示具体根因是否确认 |
| `root_cause` | 字符串或 `null` | 已确认的具体原因及关键因果机制；未确认时为 `null` |
| `stop_reason` | 字符串枚举或 `null` | 仅下表三种原因；调查继续时可为 `null`，纯执行异常且无适用诊断停止原因时也可为 `null`，需结合任务终态判断，见第 8.4 节 |
| `explanation` | 字符串 | 为什么确认或无法确认、为什么停止，以及影响结论的必要局限 |

删除事故级引用字段不代表删除证据。Report 仍接收完整诊断状态，结合假设、关系及共享证据理解结论，不将这四个字段当作唯一输入。必要局限写入 `explanation`，不另设 `limitations`，也不重复复制所有假设的缺口。

#### 三种停止原因

| `stop_reason` | 含义 |
|---|---|
| `root_cause_confirmed` | 已满足具体根因确认标准，无需继续调查 |
| `budget_exhausted` | 达到轮数、实际工具调用次数、总时长上限，或达到第 8.2 节内部往返上限且无法继续合法推进；在 `explanation` 中说明实际触及哪项预算，不能仅因内部计数为 2 就禁止有效工具查询 |
| `critical_data_unavailable` | 必需的关键验证数据无法获得，且没有有效替代路径 |

轮数或工具调用额度耗尽，限制的是继续启动新批次或新工具调用，不是立即丢弃最后一批结果。时间允许时先完成有效分析及有限内部调整；若确认根因，使用 `root_cause_confirmed`，若仍缺事实且额度不允许补查，使用 `budget_exhausted` 并说明触及哪项限制。硬时间截止始终优先，不能为分析自动延长。

**已明确取消：** `no_actionable_query / no_progress / execution_error` 不作为事故级停止枚举；不考虑“连续两轮无实质进展”，不维护连续无进展轮数。

单次工具失败不自动意味着关键数据不可用，也不意味着整体调查必须结束。存在其他有效验证路径时仍可继续。不得将所有“无法继续”都强行归类为 `critical_data_unavailable`：只有关键数据确实无法取得且无替代路径时才能使用。

这些原因不替代后台任务的失败、超时或取消状态。没有有效查询时，先按第 8.2 节给予有限的内部回流机会；确实触及内部往返上限后，可使用 `budget_exhausted`，不能第一次遇到无查询就假称预算耗尽。非法输出等执行异常不因此被包装成正常停止，其处理仍需工程设计；不能伪造停止原因，也不能擅自恢复已删除的枚举或无进展规则。

#### `root_cause` 的写法

采用可空字符串，不拆成新的嵌套对象。通常用一到三句话表达：**具体对象与原因 → 关键作用机制 → 本次故障表现**。这是写作指引，不是固定字数或额外字段要求。

- `confirmed` 时，填写有证据支持的具体因果解释，不只写“数据库问题”“发布异常”等故障标签。
- `unconfirmed` 时，`root_cause` 为 `null`；已知事实和主要候选放入 `explanation`，不能把疑似原因填成已确认根因。
- 只确认连接池耗尽，不等于已经确认为什么耗尽；不能为了写完整因果链而编造配置错误、连接泄漏或慢查询。
- 已确认具体技术原因后，不强制无限追问组织或人员原因，例如“为什么开发者修改了配置”。
- 不写工具执行过程、逐条证据、预算或停止原因，也不写回滚、扩容等处置建议。
- 多个因素确有证据表明共同致因时，可以在一段文字中说明共同作用；不得把尚未区分的竞争解释拼成共同根因。

以下仅为写法示例，只有相应事实和因果环节已获证据支持时才可用于实际结论：

> payment-service 本次发布将连接池上限从 100 降至 20，导致高峰期间可用连接不足、请求等待连接并超时，最终触发支付接口延迟告警。

未确认的结构示例：

```json
{
  "conclusion_status": "unconfirmed",
  "root_cause": null,
  "stop_reason": "critical_data_unavailable",
  "explanation": "已确认连接等待导致请求超时，但无法取得受影响实例的实际生效配置，且当前无有效替代验证路径，尚不能区分连接池上限降低与其他容量不足原因。关键验证数据不可用，本次结束调查。"
}
```

#### 确认标准与职责边界

事故级 `confirmed` 仍须满足第 5.3 节的原因具体、因果链有证据、无未解决关键反证或主要竞争解释三项标准。某个假设为 `supported`、关系为 `causal_link`，或工具调用全部成功，都不能自动确认事故根因。

Evidence Reasoning 综合假设、证据与关系形成事故级判断；程序控制层核实预算等停止事实并执行收尾，不能自行升级根因结论；Report 表达已有判断，不首次发明原因或改写确认等级。调查期间可保留最新有效判断，停止时明确实际原因，并按第 5.5 节将未决假设收尾为 `unresolved`。

若已有返回结果尚未分析，应在 `explanation` 中明确局限。最后分析无法完成时，保留最后一次有效判断及其适用范围，不声称结论已经考虑全部已存结果，也不为收尾自动延长预算。

## 6. 模板和项目知识建议

### 6.1 简短、粗粒度模板

预置模板库不是诊断的必要依赖，以下保留为可选参考建议，不要求本期先构建、检索或注入模板库。没有模板时，仍按第 8 节先获取证据，再结合告警与项目知识生成初始假设。

建议内容为：名称、适用场景、可能原因、排查建议。

```text
名称：数据库连接池问题
适用场景：获取连接超时、连接等待增加或持续满载。
可能原因：配置不当、连接未归还、慢查询导致长期占用等；不是完整清单。
排查建议：结合连接池配置、使用与等待情况、请求量及查询耗时形成具体假设。
```

模板是生成方向，不是判定规则，不保存本次证据或 `hypothesis_status`。参考模板不等于假设成立。推荐查询描述信息需求即可，不写死服务名、指标名和参数。

模板以 JSON 存储、最多选择 3 个、关键词匹配等是助手后续建议，尚未批准。知识较少时可以直接注入，不必为了选取模板新增复杂检索系统。

### 6.2 已确认的项目知识输入

讨论方向为：

- 如采用可选模板，可提供通用故障类别参考，但不是诊断启动前提。
- 项目组提供业务和运行知识，校正服务拓扑、指标目录。
- LLM 根据项目知识和现场证据生成具体假设。

项目组不必穷举故障答案。建议提供服务职责、同步/异步调用、超时与重试、降级行为、日志字段含义、默认配置和历史经验。

用户确认采用一份小型 YAML 项目知识文件，以结构化项目/服务外壳配合自然语言说明，初版采用 `project_overview` 和 `services`，每个服务下使用 `description`。不把职责、超时、重试、配置等拆成大量必填字段；未知内容留空，不由模型补写成项目事实。现有拓扑和指标目录不重复抄写，知识仅补充依赖的同步/异步性质、失败传播等语义。

推荐内容包括服务职责和关键业务流程、调用与失败处理、超时/重试/降级机制、关键配置语义、日志与指标的特殊含义。不要求穷举故障答案，也不强制每个服务填满所有类别。

以下仅为格式示意，不代表当前项目的已核实事实，服务标识应使用实际目录中的值：

```yaml
project_overview: |
  说明核心业务流程和理解告警所必需的项目背景。
services:
  example-service:
    description: |
      填写已核实的服务职责、同步或异步调用及失败传播机制。
      补充关键配置和日志字段的含义；未知内容不要编造。
      文档默认配置不代表故障时的实际生效值。
```

`prepare_context` 在任务开始时读取并固定知识快照，同时装配已有拓扑和指标目录。同次调查始终使用该快照，不因文件中途修改而改变依据。知识量小，直接向相关模型节点提供完整知识，不引入 RAG、筛选裁剪系统或预置模板库作为必要依赖。

| 节点 | 使用目的 |
|---|---|
| `build_queries` | 理解查询对象、配置语义及观测口径；具体参数仍由工具能力和目录校验 |
| `revise_hypotheses` | 结合现场证据形成符合项目机制的解释 |
| `assess_hypotheses` | 判断机制是否合理，识别仍需现场证据验证的环节 |
| Report | 解释业务影响及建议前提，不借知识补造事故事实 |

**项目知识不是本次事故证据。** 文档写“通常会重试”不能证明本次发生了重试放大；默认超时或连接池大小也不等于实际生效值。知识不放入共享证据集合，不伪装成 `evidence_id` 引用；可以在说明中标明“依据项目知识”，事故确认仍需现场证据。

具体文件路径和加载方式在工程方案中对齐现有配置机制：YAML 用作知识内容文件，不另建第二套应用配置入口；知识文件定位如需配置，应沿用项目既有 JSON 配置加载规则。实际知识内容需由项目组提供或核实，不能从评测答案反推。

## 7. 工具参数构建方向

此前已讨论并接受差异化参数构建，不强迫三个工具采用统一方式：

| 工具 | 目标构建方式 |
|---|---|
| SearchLog | 程序提供基本范围约束；首轮由 LLM 结合告警、项目知识等提出查询条件，后续结合假设和证据缺口构造 |
| QueryMetric | LLM 选择服务、指标及必要维度，程序按指标目录校验并构造合法调用 |
| QueryChange | 程序构造为主，初始查询告警服务及一级依赖；后续根据推理目标补查 |

后续日志查询必须允许有依据地追查其他服务或调用链，不能永远强制与原告警服务条件相交，否则跨服务日志会被过滤掉。

服务和指标名称必须有目录、拓扑或证据依据。工具不能查询的内容应记录为能力缺口，不能编造工具或参数。

当前 QueryMetric / QueryChange 为本地 Mock，不走 MCP；SearchLog 经现有 MCP 接口执行。目标方案已确认批内独立查询并行、批末统一分析，依赖查询放入后续批次；当前实现仍是串行，不能称为已完成并行改造。

## 8. 已确认的整体流转与待定工程细节

### 8.1 已确认的节点分工

以下是用户已确认的目标职责，替代此前 `prepare / planner / executor / evidence_reasoning / report` 五节点草案及职责混合的备选方案，不代表当前代码已经实现。既有章节中的 Evidence Reasoning 是推理能力的泛称；新方案的证据评估和事故级判断由 `assess_hypotheses` 承担，生成与细化由 `revise_hypotheses` 承担。

| 节点 | 已确认职责 | 能力边界 |
|---|---|---|
| `prepare_context` | 装配告警、项目知识、已有证据、工具能力及预算 | 不依赖预置假设库，不用规则推断根因 |
| `assess_hypotheses` | 先用证据更新已有假设及关系，再判断事故根因；未确认时判断缺证据还是需要调整假设 | 调用 LLM 综合推理，不直接执行工具，不首次生成另一套候选 |
| `revise_hypotheses` | 首次生成假设、细化已有假设、必要时新增假设；只输出解释文本的新增与修改项 | 不写证据判断，不合并重复解释，不每轮重建全部假设，不把合并交给其他节点 |
| `build_queries` | 根据问题、告警、知识、证据、查询历史及工具能力构建 `query_plan`，包含可执行调用及未满足需求 | LLM 与程序共同完成，不改写诊断结论，不编造工具或参数，不自行决定整体停止 |
| `execute_queries` | 校验并执行本批工具调用，执行后保存查询记录及完整结果 | 独立查询有界并行，暂不重试，不用命中规则判根因 |
| `finalize` | 核实停止事实并完成未决假设收尾，保留原因与缺口 | 程序逻辑为主，不升级根因结论 |
| `report` | 程序固定结论头部，LLM 组织解释正文，失败时程序兜底 | 不首次推断根因，不丢弃关键竞争解释；详见第 8.4 节 |

`finalize` 的职责及独立注册为程序图节点的实现方向均已确认，见第 8.6 节；该节点不调用 LLM。节点职责确定不等于每个节点都需要一次 LLM 调用。

### 8.2 首轮与后续循环

#### 首轮：先采证，再生成初始假设

**已明确确认：首轮尚无假设，先依据告警、项目知识等相关信息调用工具，获取证据后再生成初始假设。** 这替代之前“先进入评估节点选择是否查询”或“直接根据告警先生成候选”的首轮方案。

```text
prepare_context
    → build_queries
    → execute_queries
    → revise_hypotheses（生成初始假设）
    → assess_hypotheses
```

- 首轮 `hypothesis_ids` 为 `[]`，不为挂载查询而虚构假设。
- 初始假设结合实际返回、告警和项目知识生成，不依赖预置模板库。
- 首轮无法构造任何调用但有明确未满足需求时，返回 `assess_hypotheses` 判断替代采集路径或停止条件，假设列表保持为空，不在尚未采证时生成初始假设；详见本节查询计划契约。
- 正常路径按首轮采集证据足以形成初始假设设计；本期不展开全部工具失败、全部空结果或证据不足时的专门补采流程。用户已确认下述最低退出路径，不保证真实环境总满足正常路径，也不允许异常时伪造证据或假设。
- 形成初始假设后使用已有证据评估；若已经满足确认标准，不强制再执行一批验证工具。

#### 已确认的首轮最低退出路径

用户经整体审阅后确认：不新增专门首轮补采流程，只补齐采证或假设初始化无法完成时的退出路径。

| 首轮情况 | 已确认处理 |
|---|---|
| 部分调用失败，但其他调用返回业务数据 | 保存成功结果及失败记录，继续生成并评估假设，不因单次失败终止整批 |
| 全部调用失败，或全部成功但业务结果为空 | 不进入假设生成节点，假设列表保持为空，直接程序收尾及兜底报告 |
| 有业务数据，但模型无法形成有依据的初始假设 | 允许返回空的假设增量，不强迫编造，也不仅因没有候选而触发输出修正；按诊断初始化未完成收尾 |
| 已形成假设，但证据不足以确认具体根因 | 继续已确认闭环，正常结束后的未确认不自动判定执行失败 |

无初始假设时，报告明确说明“尚未形成有效根因判断”，保留实际获得的数据、空结果及失败原因，不拼凑因果结论：

- 若只是首轮采证不足或暂时失败，且没有真实适用的诊断停止原因，`stop_reason = null`，任务为 `failed`，说明诊断初始化未完成；不是因为根因 `unconfirmed` 而判失败。
- 若确有关键数据不可用或预算耗尽的事实，使用相应既有停止原因，按正常未确认诊断收尾；不能仅凭全空结果或单次错误推定关键数据永久不可取得。
- 核心模型接口失败或非法输出仍按既有执行异常规则处理，与合法返回空初始假设增量区分。
- 不新增停止枚举、不自动重试、不将空结果当作反证，也不增加专门的首轮补采循环。首轮构建无调用但有未满足需求时，仍使用已确认的有限内部回流，与实际执行后没有业务数据的退出路径区分。

**已确认的取舍：** 首轮数据不足时，本期可能提前退出；这是当前范围的最低闭合，不表示未来不能增加补采能力。程序只检查业务结果是否为空等结构条件，不凭非空结果、数量阈值或工具成功次数保证能够形成正确假设。相关测试须覆盖部分成功、全部失败、全部空结果、合法空初始假设增量，以及明确停止事实与初始化失败的区分。

#### 后续：评估、调整假设或补证据

```text
assess_hypotheses
    ├─ 满足停止条件 → finalize → report
    ├─ 需要生成/细化解释 → revise_hypotheses → assess_hypotheses
    └─ 需要补充事实 → build_queries → execute_queries → assess_hypotheses
```

评估节点的内部顺序明确为：

1. 结合历史与新增证据，更新已有假设的状态、理由、证据引用、缺口及假设关系。不局限于本批查询直接关联的假设，新证据影响的其他候选也应更新。
2. 基于更新后的判断检查具体根因是否确认，形成事故级结论。
3. 未确认时区分“缺关键事实”与“现有解释不充分”：前者构建查询，后者要求细化或新增假设；满足预算或关键数据不可用条件时收尾。

“信息足够形成假设”不等于“信息足够确认根因”，不能只用一个笼统的“信息是否足够”判断替代上述区分。

调整假设后返回评估节点，因为已有证据可能足以支持或反驳新解释，不强制每次调整后都查工具。内部循环按本节已确认的两次往返额度控制，不恢复已取消的连续无进展规则。

#### 已确认的内部往返额度

**每两个实际工具执行批次之间，最多允许两次不经过工具执行、又返回评估节点的内部往返。** 假设调整往返与无可执行查询的回流共用程序计数 `internal_steps_used`，不新增假设、查询记录或证据字段。调查开始时计数为 0。

| 路径或事件 | 计量规则 |
|---|---|
| `assess_hypotheses → revise_hypotheses → assess_hypotheses` | 每次往返消耗一次额度 |
| `assess_hypotheses → build_queries → 无可执行调用 → assess_hypotheses` | 带明确未满足需求的回流消耗一次额度 |
| 首轮构建无调用，带明确未满足需求返回评估 | 同样使用内部额度，不能成为不计数的空转入口 |
| 构建查询后实际执行工具批次，再进入正常分析 | 不消耗内部额度；实际批次执行结束后重置为 0 |
| 首轮采证后首次生成假设并进入评估 | 必要初始化路径，不消耗内部额度 |
| 非法 JSON、无效参数等模型输出修正 | 不算正常内部往返，每次诊断节点输出最多针对性修正一次，占用阶段时间，不重置内部额度，见第 8.4 节 |

实际工具批次即使全部失败，也会提供新的执行失败信息，批次结束后允许重置内部计数；所有实际发起调用仍计入 20 次预算，工具仍不重试。空计划、仅再次读取已有证据、没有实际发起调用的批次均不能重置计数。不能安排没有调查价值的调用来重置额度。

**两次额度不是 `revise_hypotheses` 与 `build_queries` 的总调用次数上限。** 查询构建只有在没有可执行调用、需要返回评估时才形成受限的内部往返；能进入实际工具执行的正常查询路径不消耗该额度。

两次假设调整后的示例：

```text
评估 → 调整假设 → 评估（已用 1 次）
                 → 再调整假设 → 评估（已用 2 次）
                                  ├─ 满足确认或其他停止条件 → 收尾
                                  └─ 构建查询
                                       ├─ 有有效调用 → 执行 → 计数重置 → 分析
                                       └─ 无可执行调用 → 不再回评估，按内部预算收尾
```

在总时长等硬预算允许时，最后一次往返后的评估仍必须完成，不能新假设刚被初始化为 `pending` 就跳过判断。达到 2 次后不再允许第三次假设调整，但仍允许构建有价值的查询；构建后仍无可执行调用时，不再给予第三次回流。若评估仍要求被禁止的内部调整且不能转向合法查询或其他正常停止路径，也按内部预算触顶收尾。

程序将剩余额度提供给评估节点，并在路由和执行前进行硬检查。次数触顶不自动反驳假设，也不自动确认根因；收尾时使用现有 `budget_exhausted`，在事故级 `explanation` 中说明已触及内部往返上限、当前仍未确认及未满足需求。未决假设按第 5.5 节转为 `unresolved`，保留理由和缺口。

该约定明确扩展 `budget_exhausted` 的含义，不新增停止枚举。它统计可观测的内部操作，不让模型判断“有没有实质进展”；即使每次提出新解释，也受额度约束。硬截止时间优先，不能为了完成最后评估自动延长 8 分钟。

#### 已确认的假设写入职责与增量更新契约

**`revise_hypotheses` 只负责提出或修改解释本身，`assess_hypotheses` 负责证据判断，程序负责 ID、初始化及保存。** 调整节点不直接填写完整六字段，不自行支持或反驳假设。

| 假设字段 | 负责方 | 规则 |
|---|---|---|
| `hypothesis_id` | 程序 | 新增时分配稳定唯一 ID，细化时按下述边界保留 |
| `statement` | `revise_hypotheses` | 首次生成、细化或新增具体解释 |
| `hypothesis_status` | 程序初始化，`assess_hypotheses` 评估更新 | 新增或实质性细化后为 `pending`，调整节点不能确认或反驳；`finalize` 仍按已确认规则收尾 |
| `assessment` | `assess_hypotheses` | 程序先写入待评估说明，评估节点随后写入判断依据和局限 |
| `evidence_links` | `assess_hypotheses` | 程序先置空，评估节点重新关联并解释适用于当前假设的证据 |
| `gaps` | `assess_hypotheses` | 程序先置空，评估节点填写当前解释的关键缺口 |

**同一解释的细化保留 ID，改换原因则新增假设。** 例如：

- “发布降低连接池上限”细化为“发布将连接池上限从 100 降至 20”，保留 ID。
- “连接池容量不足”细化为“发布降低连接池上限造成容量不足”，可以保留 ID，但更具体的原因必须重新评估，不能继承原来的 `supported`。
- “发布降低连接池上限”改为“连接泄漏导致可用连接减少”，属于不同原因，应新增 ID，不覆盖或删除原假设；原假设是否被反驳仍由证据评估决定。

不新增假设版本字段，不引入合并操作。仅措辞润色而无实质变化的内容，不作为一次假设调整。程序可校验 ID 和结构，但“细化还是更换原因”的语义判断仍需模型遵守约束，不能声称机械校验可以保证。

新增或实质性细化后，程序统一初始化判断字段并立即返回评估节点。细化后的结构示例：

```json
{
  "hypothesis_id": "H1",
  "statement": "发布降低连接池上限，导致容量不足和请求等待。",
  "hypothesis_status": "pending",
  "assessment": "假设解释已更新，等待结合现有证据重新评估。",
  "evidence_links": [],
  "gaps": []
}
```

新增项的 `assessment` 相应说明“假设已生成，等待结合现有证据评估”。此时 `pending` 指当前这版解释尚未完成评估，不声称此前从未调查；空的证据关联和缺口列表表示等待重新建立判断，不表示没有相关证据或不存在缺口。

原始证据和查询记录不删除，评估节点使用完整相关证据重新判断，不要求重新执行工具。未修改的假设不重置。这里的重置针对解释发生变化，与整体停止时必须保留已有理由和缺口的收尾规则不同。

**调整节点只返回增量，不返回完整假设列表。** 已确认的节点输出结构如下，两个字段均为列表，无对应操作时为 `[]`：

```json
{
  "new_hypotheses": [
    {
      "statement": "连接未及时归还，导致可用连接持续减少并引发等待超时。"
    }
  ],
  "revised_hypotheses": [
    {
      "hypothesis_id": "H1",
      "statement": "本次发布降低连接池上限，导致高峰期间容量不足和请求等待。"
    }
  ]
}
```

这只是节点交接格式，不新增两套持久化假设集合。程序为新增项分配 ID，校验修改项 ID 存在且不重复修改，应用新增和细化并初始化判断字段，保留其他假设不变，然后进入 `assess_hypotheses`。历史保存方式仍待工程设计。

`revise_hypotheses` 不修改假设关系或事故级结论。解释变化后，`assess_hypotheses` 必须重新检查相关 `causal_link / competing`，不能因 ID 未变就沿用旧关系。重新评估完成前，旧关系和旧事故级结论不能被当作针对新解释的有效判断；Report 不得混用新假设与旧结论。当前工作状态与最后一次有效评估快照按第 8.4 节分开保留；具体 checkpoint、保存与恢复机制仍待工程设计，不增加假设顶层字段。

#### 已确认的下一步决策结构

`assess_hypotheses` 在更新假设、关系和事故级结论之外，输出调查级 `next_step` 对象，表达“下一步做什么、为什么做、希望解决什么问题”。不新增假设字段，也不提前创建执行后的查询记录。

| 字段 | 类型 | 含义 |
|---|---|---|
| `action` | 字符串枚举 | 仅 `build_queries / revise_hypotheses / finalize`，选择一个后续分支 |
| `reason` | 字符串 | 选择该分支的理由，不是另一份根因结论 |
| `requests` | 对象列表 | 本次希望下游处理的问题；顺序表达处理优先次序，结束时为空列表 |

`requests` 每项仅包含：

| 字段 | 类型 | 含义 |
|---|---|---|
| `hypothesis_ids` | 字符串列表 | 问题涉及的假设 ID；无法被现有假设解释的新现象可以为空列表 |
| `requirement` | 字符串 | 要解决的具体问题及必要的判别意义或约束 |

三个动作的语义：

- `build_queries`：当前解释仍值得验证，但缺少现场事实。请求说明要查明什么及其判别价值，不提前规定工具名称、指标名或完整参数。
- `revise_hypotheses`：已有证据暴露解释缺口，需细化或新增假设。请求指出现有解释哪里不足、需要解释什么，不笼统要求“再想几个原因”，不要求合并假设。
- `finalize`：满足已确认的停止条件，`requests` 为 `[]`。根因和停止原因仍保存在事故级结论中，不在 `next_step` 中重复维护。

补证据示例（仅说明结构，不代表真实事故判断）：

```json
{
  "action": "build_queries",
  "reason": "容量下降与请求增长都能解释连接等待增加，当前缺少区分两者的现场事实。",
  "requests": [
    {
      "hypothesis_ids": ["H1", "H2"],
      "requirement": "查明受影响实例故障前后的连接池实际生效上限及同期请求量变化，用于区分两个解释或判断是否共同作用。"
    }
  ]
}
```

假设的 `gaps` 保留该假设当前重要的未解决问题；`next_step.requests` 只选择本次值得推进的问题及整体解释缺口，不复制全部 `gaps`。一个请求可以拆成多个工具调用，多个请求也可以通过一次调用解决，列表长度不等于调用次数。

`build_queries` 若无法满足信息需求，应通过下述 `query_plan.unmet_requests` 如实反馈，不能将“发布记录中的配置”悄悄当作“实例实际生效配置”。`revise_hypotheses` 根据请求形成解释后返回评估节点，不直接确认根因。

每次有效评估更新当前 `next_step`，历史是否随现有步骤记录保存留待工程实现；不为此建设独立记录系统。首轮按告警和项目知识构建查询，不要求先运行评估节点制造一个 `next_step`。

#### 已确认的查询计划与未满足需求

`build_queries` 输出调查级 `query_plan`，仅包含两个对象列表：`calls`（本批可执行调用）和 `unmet_requests`（本批未满足的信息需求）。不额外增加计划状态或下一步动作，由程序结合列表内容和预算决定执行还是返回评估。

`calls` 每项仅保留以下四字段，复用执行后查询记录的含义：

| 字段 | 类型 | 含义 |
|---|---|---|
| `hypothesis_ids` | 字符串列表 | 本次调用服务的假设，首轮为 `[]` |
| `question` | 字符串 | 本次调用实际回答的问题及其判别价值 |
| `tool_name` | 字符串 | 现有且可使用的工具名称 |
| `arguments` | 对象 | 经校验的具体调用参数 |

计划中不预写 `status / status_reason`。`query_id` 由程序在准备发起实际调用时分配；分配 ID 不等于提前创建执行后记录。工具调用结束后，将实际调用信息和 `succeeded / failed` 及原因写入第 5.8 节的查询记录，完整业务返回另存共享证据。

`unmet_requests` 每项仅保留以下三字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `hypothesis_ids` | 字符串列表 | 涉及哪些假设，可为空列表 |
| `requirement` | 字符串 | 本批尚未满足的具体信息需求 |
| `reason` | 字符串 | 为什么本批无法满足，包括能力限制或前置条件尚未具备 |

以下仅为未满足需求项的结构示例，不代表实际工具能力已核验：

```json
{
  "hypothesis_ids": ["H1"],
  "requirement": "获取受影响实例实际生效的连接池上限。",
  "reason": "现有工具只能查询发布记录，不能读取实例运行时配置；发布记录无法替代实际生效值。"
}
```

`unmet_requests` 只说明本批未覆盖，不表示永远无法解决，不自动将假设设为 `blocked`，也不自动确认整体应停止。它不是现场证据，不能用于证明事故原因。

信息需求与调用不强制一一对应：一个需求可拆成多个调用，一次调用也可回答多个需求。不增加请求 ID 或复杂映射表，以关联假设和明确的问题描述表达；重要需求必须由调用覆盖，或说明本批为何未覆盖，不能静默遗漏。部分满足时，只将剩余部分记录为未满足需求。

进入 `calls` 的调用必须满足：

- 工具存在且可使用，参数合法，服务和指标名称等有依据。
- 参数不依赖本批其他尚未返回的结果；例如需要先获得 `trace_id` 的后续查询留到以后，在未满足需求中说明前置条件。
- 对当前问题有实际价值，不为产生动作而查询；不重复无价值查询，不把失败调用重试伪装成补查。
- 工具能力不足与模型生成非法参数必须区分。后者按第 8.4 节最多针对性修正一次，仍失败则异常收尾，不能包装成能力不足。

已确认的执行与回流规则如下，均须遵守程序预算约束：

| 计划结果 | 后续行为 |
|---|---|
| 有调用，无未满足需求 | 执行本批，按首轮或后续正常路径分析 |
| 有调用，也有未满足需求 | 先执行具有独立价值的部分，并将未满足需求交给后续生成和评估环节 |
| 无调用，有明确未满足需求 | 不进入执行节点；内部额度允许时返回 `assess_hypotheses`，额度已用完则保留未满足需求并按内部预算收尾 |
| 两个列表都为空 | 视为没有交付有效计划，不自动判定调查完成；按第 8.4 节最多修正一次，仍无效则异常收尾 |

部分可查时不机械执行无价值的残余调用：若某调用只有在另一个不可执行的调用成功后才有意义，就不应进入本批。后续分析必须同时获得“实际查到了什么”和“原本想查但没有覆盖什么”，不能默认完整满足了原请求。

首轮无法构造调用但有明确未满足需求时，在内部额度允许范围内，评估节点接收告警、项目知识及未满足需求，假设列表仍为空，只判断替代采集路径或是否满足关键数据不可用等已确认停止条件，不在尚未采证时生成初始假设。这是异常回流，不改变正常首轮先采证再生成假设的顺序；内部额度触顶后按真实预算事实收尾，不伪造停止原因。

查询计划、执行后记录和共享证据职责分开：计划说明准备查什么及哪些需求暂不能满足；查询记录说明实际调用及执行结果；证据集合保存实际返回内容。未执行的计划或无法构造的调用，不记为工具执行失败，也不占用实际工具调用次数。

#### LangGraph 条件边路由

目标实现通过 LangGraph 的 `add_conditional_edges()` 读取已校验的 `next_step.action`，从 `assess_hypotheses` 路由到三个合法分支，不新增调用 LLM 的路由节点：

```text
assess_hypotheses 调用 LLM
    → 校验输出并更新图状态中的 next_step
    → 条件边读取 action
    → build_queries / revise_hypotheses / finalize
```

- 模型提出下一步，程序只映射到允许的路径；条件边不重新推理、不修改假设或根因结论。
- 未知动作、非法结构、不存在的假设引用等应在评估节点返回更新前完整校验，不能靠类型注解代替运行时校验；最多修正一次，仍失败按第 8.4 节异常收尾，不默认当成正常结束。
- 路由到 `finalize` 前应核对动作理由与事故级结论的一致性，结构校验本身不保证语义正确。
- 预算是程序硬约束，按操作类型检查：轮数已达 5 时禁止启动第 6 批，调用已达 20 次时禁止新工具调用，但不因此跳过已有结果的分析；模型调用仍受总时长、内部额度等适用约束。没有新批次或工具额度且确需补查时，不再构建注定无法执行的计划，按真实事实收尾。检查不仅发生在条件边，还应在模型或工具调用发起前执行；路由本身不负责写入停止事实。
- 确定性路径可使用普通边，例如 `revise_hypotheses → assess_hypotheses`；`finalize → report` 按收尾步骤的实际实现接入。
- `build_queries` 不再无条件连接执行节点：条件路由根据有效 `query_plan` 和预算选择执行或返回评估；双空计划走第 8.4 节的修正/异常流程，不当作正常结束。
- `execute_queries` 后使用条件路由区分首轮和后续：首轮有业务结果时生成初始假设，后续回到评估节点；首轮全失败或全空结果执行本节已确认的最低退出路径，不新增专门补采分支，也不声称正常路径已覆盖所有异常。

#### 已确认的批内并行

一批查询是一次构建后准备执行的一组工具调用。**参数已经能够独立确定的调用在批内有界并行，批末统一分析；依赖前序结果的调用放到后续批次。**

```text
build_queries
    ├─ Q1 日志查询 ──┐
    ├─ Q2 指标查询 ──┼→ 本批调用均结束后，进入生成或评估节点
    └─ Q3 变更查询 ──┘
```

- 首轮根据同一告警查询日志、指标与变更，若参数均能预先确定，通常可以同批执行；不要求每批机械凑齐三类工具。
- 先查询日志获得 `trace_id`，再按该 ID 查询调用链，不能作为两个独立并行调用。应先获取和分析第一批结果，再构建下一批。
- 串行排列调用不会自动根据前一个结果重新生成后一个参数；本方案不在批内每完成一个工具就调用 LLM 重规划。
- 并行的三次调用仍计三次工具调用。发起前检查并协调剩余预算，实际发起时计数；不能各调用独立读取同一剩余额度而超出 20 次上限。
- 各调用结束后分别保存查询记录和完整结果，某个调用失败不自动阻断其他独立调用；暂不重试。正常批末等待各调用成功或失败后统一处理，不能让单个失败丢弃其他已获结果。
- 并发上限及每批调用上限暂均设为 4，不要求用满；仍遵守工具自身更严格的限制及剩余预算。单调用超时、阶段截止及迟到结果原则见本节“时间与收尾”；取消和恢复的具体执行机制仍需工程设计。不能无限等待最慢调用或延长总预算。

#### 已确认的轮数计量

**一轮是一次实际启动的工具执行批次，连同围绕这批结果进行的假设生成、评估及有限调整。** 区分“占用一轮预算”和“完成这一轮分析”：程序计数 `rounds_used` 初始为 0，本批第一个工具调用实际发起时加 1，不等到证据分析成功才计数。

同批后续调用不重复计轮。批次身份由程序保持，即使受并发限制分波执行也仍算一轮，不由模型随意重新划分；一批三个调用消耗 1 轮和 3 次工具调用。后续新增查询构成新批次，不能以沿用旧批次身份绕过上限。

| 情况 | 计轮规则 |
|---|---|
| 首轮采证、生成初始假设并评估 | 1 轮，不是预算外采集 |
| 计划已构建，但任何调用都未发起就被拦截或取消 | 不计轮 |
| 无可执行调用，返回评估 | 不计轮，按内部往返额度规则处理 |
| 同批全部成功、部分失败、全部失败或正常空结果 | 都计 1 轮；实际调查尝试已发生 |
| 仅发起部分调用后批次被中断 | 已计 1 轮，工具次数仅计实际发起部分 |
| 工具已执行，但后续模型分析失败 | 已消耗 1 轮，不因分析失败返还预算 |
| 评估后调整假设，再利用已有证据评估 | 不新增轮数，消耗内部往返额度 |

首轮流程示例：

```text
构建首轮查询                      不加轮
    → 发起本批第一个调用           rounds_used = 1
    → 完成本批执行
    → 生成初始假设                 不额外计轮，也不消耗内部额度
    → 评估
    → 如需细化，再调整并评估       仍为第 1 轮后的分析，消耗内部额度
    → 实际发起下一批第一个调用     rounds_used = 2
```

**`rounds_used = 5` 表示不得启动第 6 批，不表示立即终止第 5 批或其分析。** 在工具调用额度、单调用超时及总时长允许范围内，仍可完成第 5 批已安排的调用，分析返回结果、更新假设和关系及事故级结论，并使用剩余内部额度生成或细化假设、再利用已有证据评估，最后收尾和报告。

若最后评估需要补充现场事实，但已无新批次额度，程序不再调用 `build_queries` 生成无法执行的计划，按 `budget_exhausted` 收尾。第 5 批出现关键新事实时，不能仅因轮数已满就禁止解释这些事实；但内部调整仍受两次额度限制，不能无限推理。

各预算独立生效，不能相互兑换：

- 5 轮限制实际启动的工具批次数；第 5 轮只用了 12 次调用，也不能开启第 6 轮。
- 20 次限制实际发起的工具调用数；第 3 轮已用满 20 次，也不能借剩余轮数继续调用。
- 内部 2 次限制不执行工具的内部往返；剩余额度可用于最后一批后的有限分析，不产生新批次权限。
- 8 分钟包含报告，是时间硬边界，起点与阶段预留见下文“时间与收尾”；进入时间收尾阶段后不再启动假设调整，即使轮数或内部额度仍有剩余。不能以本轮尚未分析完为由自动延长。

最后有效分析确认根因时，可按 `root_cause_confirmed` 结束；仍缺证据而无法再查时，按 `budget_exhausted` 说明实际耗尽的额度。计数与并发发起、中断恢复如何保持一致仍需工程实现，但不得改变上述预算语义。

#### 时间与收尾

本次讨论采用以下时间边界与兜底方向。**8 分钟包含诊断和报告，不是查询满 8 分钟后再追加收尾时间。** 下列秒数作为初始工程配置，未经实际模型或工具延迟验证，不能保证模型必然及时返回；本节记录目标设计，不代表现有代码已实现。

**计时起点：** 后台任务实际开始执行 `prepare_context` 时确定固定截止时间，不从用户提交请求时起算。执行前排队不计入；知识和证据装配、模型和工具调用及等待、输出修正、内部调整、最终分析和报告均计入。节点切换或任务恢复不能重新获得完整 8 分钟。

| 阶段 | 相对任务实际开始的时间 | 允许的操作 |
|---|---|---|
| 正常调查 | 0 至 6 分 30 秒 | 查询构建、工具执行、评估及有限假设调整 |
| 最终分析与收尾 | 6 分 30 秒至 7 分 30 秒 | 汇总已返回信息，必要时完成最后一次评估及程序收尾 |
| 报告 | 7 分 30 秒至 8 分钟 | 表达有效结论；模型无法及时完成时使用程序兜底 |

阶段边界是最迟限制，不要求等待到该时刻。提前确认根因或满足其他停止条件时，立即收尾和报告；任何路径均不得自动延长总时长。

**探索截止后的行为：** 到 6 分 30 秒不再启动工具调用、查询构建或假设调整，收集已返回结果、失败信息及未满足需求。有未分析证据或待评估的新假设时，执行最后一次 `assess_hypotheses`；已有有效判断已覆盖全部结果时，不强制重复调用模型。最后评估只依据当前信息形成判断与缺口，不再安排调查动作。轮数满后允许的内部调整仍受时间阶段限制，进入时间收尾阶段即不再启动调整。

**单次超时：** 工具及普通诊断 LLM 调用的初始超时上限均为 60 秒，实际可用时间取单次上限与当前阶段剩余时间的较小值。最终分析不得侵占报告阶段，报告不得超过总截止时间。不能在探索仅剩 15 秒时仍给调用完整 60 秒。工具超时记录 `failed`，不自动重试，也不自动认定整次调查失败；模型超时不能伪造有效输出，按异常与兜底路径处理。

**运行中调用及迟到结果：**

- 阶段截止时请求取消未完成调用；取消请求不保证远端已经停止，不能声称远端一定取消成功。取消协调及本地记录的具体实现仍待确定。
- 已发起调用仍计入次数，已启动批次仍计轮；超时且无正常返回的查询记为 `failed` 并保留原因，未发起的调用不伪装成失败。
- 已获得的完整或部分业务数据依照既有规则保存；最后分析开始后才到达的数据不能静默并入该次判断。
- 能够保留的迟到结果须明确未纳入最终分析，具体保存位置及已分析范围标记沿用后续执行记录设计，不新增假设字段。

**报告兜底与状态一致性：** 预留时间不保证模型返回，因此需要不依赖模型的简短程序兜底报告，直接表达已有事故级结论、有效假设判断及缺口，不创造新原因。报告生成失败不等于诊断结论失败，已有效确认的根因不能仅因报告超时而改为未确认。正常报告采用程序固定权威结论头部、LLM 组织解释正文，失败时程序兜底，具体内容及边界见第 8.4 节。

若最后评估也失败，按第 8.4 节使用最后一次有效评估快照，标明未分析结果及适用范围；不能混用新假设与旧关系、旧事故级结论，也不能把旧判断当成已涵盖新事实。快照的持久化与恢复机制仍需工程设计。硬截止后不再依赖新的模型调用，程序兜底不构成额外调查或自动延长预算；终态持久化、事件交付和取消协调的工程边界仍需明确。

**停止原因：** 最后有效分析确认根因时使用 `root_cause_confirmed`；已确认关键数据不可用且无替代路径时使用 `critical_data_unavailable`；因时间限制无法继续验证时使用 `budget_exhausted` 并注明时间限制。在 6 分 30 秒结束探索时，应说明“已达到探索阶段截止时间，剩余总时长用于最终分析和报告”，不能声称 8 分钟已经全部耗尽。非时间原因的模型错误仍按任务异常处理，不能伪造预算耗尽。

#### 批次大小与并发上限的讨论澄清

**用户最新确认：每批最多 4 次调用、最多 4 次并发，暂按此配置。** 这是工程初始值，没有实测依据证明 4 最合适。不能因为总调用上限为 20 次、调查最多 5 轮，就反推每批必须固定 4 次；各项都是保护上限，不要求平均分配或用满。

| 概念 | 控制内容 | 区别 |
|---|---|---|
| 每批调用上限 | 一次规划、执行后统一分析的调用数量 | 影响一次提前安排多少查询，以及多久利用新证据调整方向 |
| 并发上限 | 同一时刻执行的调用数量 | 主要限制同时占用的连接、接口额度与外部查询负载 |

两项不必相同。例如每批 8 次、并发 4 次意味着部分调用批内排队，而不是同时执行 8 次；这只是解释差异，不是新的已选数值。此前建议两项都取 4 是为了简化执行，不是诊断能力上的必要条件。

较大批次的主要取舍：

- **提前使用更多预算：** 本批调用根据同一份已有信息规划。某个结果即使足以排除一个候选，其他已经发起的相关查询也来不及根据该结果调整，可能产生冗余。大批次不必然无效，关键仍是调用是否独立且有价值。
- **反馈可能更晚：** 批末统一分析需等本批调用结束或超时。更多调用可能遇到慢调用或因并发限制排队，推迟有效判断；不能据此断言批次越大必然越慢。
- **并发负载需单独控制：** 更大并发可能触发限流、连接限制或观测系统负载问题，取决于真实工具能力，不能仅凭本地 Mock 的速度判断。该风险主要由并发上限控制，不必只靠缩小批次解决。
- **评估输入可能增加：** 完整返回的数量和大小会影响分析耗时与上下文使用，但调用次数不是数据大小的准确代理。没有测量时，不能声称超过 4 次调用就必然撑爆上下文，也不能据此压缩或静默截断日志。
- **也有执行效率收益：** 多个查询都能独立提供有效信息时，大批次可减少多轮规划和评估的模型调用及往返等待，避免人为拆批后立即补查。需要平衡一次多取信息与尽早调整调查方向的价值。

实际批次大小应在上限 4 内依据当前独立且有价值的查询数量决定，不机械凑满，也不按假设平均分配调用。继续遵守整体预算、工具能力约束与批末分析原则；工具有更严格并发限制时按更严格限制执行。

用户经整体审阅后确认：构建前提供剩余批次、调用及并发额度；超额计划最多针对性修正一次，仍非法则异常收尾，不随意裁剪调用。构建节点在额度内优先选择有价值的查询，未覆盖需求必须通过 `unmet_requests` 反馈。相关更新与兼容方案见第 8.4 节，不改变预算硬检查及实际发起计数原则。

### 8.3 数据结构方向

假设顶层字段见第 5.6 节，共享证据四字段及整份结果引用见第 5.7 节，查询记录七字段与执行后记录约定见第 5.8 节，调查级假设关系的两种类型与五字段见第 5.9 节，事故级结论四字段及三种停止原因见第 5.10 节。整体审阅已确认第 8.4 节的嵌套字段、更新和适配原则；以下汇总已确认的结构方向，具体模型输出 schema、校验与存储接口仍须进入工程规格：

- 假设：仅保留 `hypothesis_id / statement / hypothesis_status / assessment / evidence_links / gaps` 六个顶层字段，不设 `scope`；已确认的嵌套结构见第 5.6 节。
- 假设调整输出：`new_hypotheses` 每项只含 `statement`，`revised_hypotheses` 每项含 `hypothesis_id / statement`；程序增量应用并重置待评估字段，不重复存储整套假设，见第 8.2 节。
- 查询计划：`query_plan.calls` 每项为 `hypothesis_ids / question / tool_name / arguments`，`unmet_requests` 每项为 `hypothesis_ids / requirement / reason`；计划不预写执行状态，未满足需求不是现场证据，见第 8.2 节。
- 查询记录：`query_id / hypothesis_ids / question / tool_name / arguments / status / status_reason`，执行结束后写入，仅成功或失败两种状态，暂不重试。未执行计划与执行中状态不放入查询记录。
- 证据：仅保留 `evidence_id / query_id / kind / data`，不设 `source / coverage`；通过 `query_id` 关联执行上下文，假设只引用整份结果。
- 假设关系集合：`from_hypothesis_id / to_hypothesis_id / relation_type / explanation / evidence_ids`，仅 `causal_link / competing` 两种类型；关系存在不代表已证实。
- 分析结果：假设及关系更新、确认标准检查及事故级结论；下一步使用已确认的 `next_step`（`action / reason / requests`），每项请求为 `hypothesis_ids / requirement`，见第 8.2 节。
- 预算：`rounds_used`（初始为 0，每批首个实际调用发起时加 1，上限 5）、实际调用次数、截止时间及内部往返计数 `internal_steps_used`（上限 2，实际工具批次结束后重置）；不维护连续无进展轮数。
- 事故级结论：仅 `conclusion_status / root_cause / stop_reason / explanation`；未确认时 `root_cause` 为 `null`，必要局限在 `explanation` 中说明。

证据保留完整返回数据，通过关联查询记录追溯工具调用，不另设来源或覆盖范围字段。工具原有的返回元信息不因字段简化而删除。现有截断摘要不能继续作为唯一推理输入。

### 8.4 模型异常、状态一致性与报告

以下规则由本次专题讨论收敛，属于目标设计，不代表已实现。不为异常处理增加假设、证据或事故级结论的顶层字段。

#### 输出修正与调用失败

| 情况 | 处理规则 |
|---|---|
| 模型返回内容，但 JSON、字段、引用、参数或节点输出约束不合法 | 每次诊断节点输出最多针对性修正一次；将原输出及明确校验错误交给模型，仍不合法则异常收尾 |
| 模型调用超时、连接失败或接口错误 | 初版不自动重试，进入异常收尾，不伪造有效判断 |
| 结构合法，但推理可能不正确 | 结构校验不能证明因果正确，仍依赖推理要求和证据审查 |
| 正常报告的模型生成失败或输出无效 | 不再额外调用模型修正，直接使用程序兜底，保留已有有效诊断判断 |

针对性修正不是无提示重跑，也不是恢复工具调用重试。修正占用当前阶段和总时长，不新增调查轮数、不计正常内部往返，也不重置其额度；阶段时间不足时不启动修正，不在失败后重置次数继续修正。工具仍暂不重试，失败如实记录，不当作反证，不自动阻断其他独立查询。相同工具和参数的重复调用应识别，不以补查名义重试失败调用；确需等待新数据后再次查询时，应明确新的信息需求。

#### 已确认的诊断专用调用策略

用户经整体审阅后确认：为诊断单独设置执行策略，不改变全项目默认配置。本节落实“不自动重试”，不表示仅删除上层重试循环就已满足要求。

| 范围 | 已确认策略 |
|---|---|
| 诊断 LLM | 创建诊断专用模型实例，显式设置 `max_retries = 0`，关闭 SDK 自动重试 |
| 诊断 MCP | 仍只使用当前用户启用的连接，在诊断客户端中设置 `retries = 0`，包括诊断过程中的工具发现；不改写用户已保存的连接配置 |
| 工具超时 | 取连接配置超时、60 秒及当前阶段剩余时间的最小值 |
| 模型超时 | 取模型配置超时、60 秒及当前阶段剩余时间的最小值；报告另受报告阶段与总截止时间限制 |
| 无效模型输出 | 保留最多一次携带原输出和明确校验错误的针对性修正；修正请求自身也禁止自动重试，报告仍直接程序兜底，不进行修正 |
| 后台诊断任务 | 保留 `max_attempts = 1`，普通失败不自动从头重跑；租约过期后的恢复执行本节已确认的任务中断恢复方案 |
| 其他功能 | 聊天、Embedding、rerank、连接管理页面检查等维持原策略，不因本次诊断改造改变 |

相同工具及参数的失败调用不能仅更换 ID 再发。确需在新的信息条件下补查时，须说明新的调查价值，按新的实际调用占用预算，不建立工具重试关联。

**已确认的取舍：** 瞬时网络错误可能使核心模型直接异常收尾，不通过自动重试提高成功率；以此保持已确认的不重试边界和可控预算。该策略不关闭既有安全脱敏、审计、用户作用域或同名工具保护。实现验证须检查底层实际请求次数，并覆盖初次请求失败、修正请求失败、MCP 发现/调用失败及其他功能原有策略不受影响，而不只断言外层方法调用次数。

#### 完整校验后应用状态

节点输出先完整解析和校验，通过后一次性应用该节点的有效状态更新。不先保存部分假设，再因其他字段出错留下半份更新；非法输出可用于错误诊断和修正，但不能进入有效诊断判断。

#### 已确认的更新与兼容方案

用户经整体审阅后确认：业务字段不扩展，评估完整更新，存储复用现有结构，前端兼容历史任务。

| 事项 | 已确认方案 |
|---|---|
| 假设评估 | `assess_hypotheses` 返回全部当前假设的判断字段，每个 ID 恰好一次，不修改 `statement`；完整校验后一次提交，不遗漏旧候选或保存半份更新 |
| 状态重开 | 调查仍在进行时，新证据或阻碍解除可使旧判断重新进入调查状态；已支持、已反驳或已结束追查的方向可以重新评估，必须说明依据；整体终态后不修改该次调查 |
| 关系维护 | 每次有效评估返回完整关系列表并替换旧列表，删除失效关系，不累加残留；校验端点、证据引用、自引用及重复关系，无方向的 `competing` 只保存一条 |
| 嵌套字段 | 证据关联为 `evidence_id / relation / explanation`，`relation` 为 `supports / contradicts / context`；缺口为 `question / why_it_matters` |
| 历史保存 | 复用步骤与 checkpoint 保存修改前后状态、有效评估及已分析证据范围，不新增假设版本字段或独立历史系统 |
| 查询与证据适配 | 复用执行步骤、审计与证据存储，适配组装七字段查询及四字段业务证据；原有 owner、task、时间等存储元数据保留，不作为新增业务字段混入 |
| 证据类别 | 事故工具证据使用 `log / metric / change`，共享契约补充 `change`；原有告警、知识引用继续保留在存储中，与现场工具证据分开 |
| 前端兼容 | 新任务显示新节点、假设状态和结论；历史任务沿用旧数据展示，不强行转换；未知节点显示原名称，不静默隐藏 |
| 查询预算 | 构建前提供剩余批次、调用及并发额度；超额计划最多修正一次，仍非法则异常收尾，不随意截掉调用；未覆盖需求必须反馈 |

模型修改假设解释后，当前旧关系和旧事故级结论立即失效；历史快照仍保留，但只能表达此前判断，不能与新解释混用。这里的失效表示不再作为当前解释的有效判断，不删除历史记录；只有完整有效评估成功保存后才建立新的有效快照。

完整评估更新的是判断字段，不将 `revise_hypotheses` 改为全量重建假设；仍由程序维护 ID 与解释写入边界，不合并假设。状态重开不绕过支持或反驳标准，也不因本轮未选中某假设就重开或结束追查。引用校验不保证因果语义正确。

**已确认的取舍：** 完整评估输出比少量局部更新更大，但减少状态遗漏和新旧判断混用。推理继续读取完整相关证据，不将前端摘要或审计摘要作为唯一输入。具体适配和一致提交使用 Repository 边界，不丢失用户权限、原始结果、失败信息或历史任务。相关验证须覆盖完整 ID 集合、状态重开、失效关系移除、历史快照隔离、业务结构适配、`change` 契约及新旧任务展示。

| 节点 | 重点校验 |
|---|---|
| `revise_hypotheses` | 新增/修改结构、修改 ID 存在性及重复修改 |
| `assess_hypotheses` | 假设和证据引用、状态枚举、事故级结论与路由的明显结构或约束矛盾 |
| `build_queries` | 工具存在性、参数合法性、已确定的计划及本批约束 |
| Report（若采用结构化模型输出） | 输出格式及与已有结论的一致性要求；校验不能保证所有语义正确 |

一次性应用是逻辑一致性要求，具体事务、checkpoint 和持久化边界仍需工程实现，不宣称仅靠结构校验即可保证保存原子性或推理正确。

#### 当前状态与有效评估快照

保留当前工作状态和最后一次有效评估快照：

- 当前工作状态包含最新假设修改、查询记录、证据和待处理信息。
- 有效评估快照包含一次成功评估后相互一致的假设、关系、事故级结论，以及该判断实际分析过的证据范围。
- 只有 `assess_hypotheses` 的完整输出通过校验并成功保存后，才更新快照；工具返回、假设修改或失败的评估本身不更新快照。
- 快照属于调查内部状态，可复用后续选定的 checkpoint 或步骤机制，不要求新建数据库表或增加假设字段。

例如，H1“连接池容量不足”已获支持并形成快照，随后被细化为“发布降低连接池上限”，当前状态重置为 `pending`。若重新评估超时，不能将旧 `supported` 赋给新的解释。快照只能表明此前的容量不足解释获得支持；报告须说明具体发布原因尚未完成验证。

原始证据、失败记录及最新修改均保留，不将整个调查回滚到旧快照。历史判断不自动适用于新事实；后续存在未分析、可能影响结论的证据时，必须明确局限，不能宣称所有关键冲突已排除。收尾仍将当前未决假设转为 `unresolved`，不能从历史快照恢复状态来覆盖当前修改后的假设。

#### 已确认的任务中断恢复方案

用户经整体审阅后确认：保存完整状态，在安全边界恢复，不自动重放中断中的外部调用。继续复用 SQLite、Repository、后台任务租约与 LangGraph，不新增存储平台。本节是目标方案，不代表现有手工 checkpoint 已具备断点续跑能力；它收口前文待定的恢复方向，具体 Repository 和图入口实现仍需进入工程规格。

| 中断位置或恢复情况 | 已确认的处理 |
|---|---|
| 节点已完成且有效更新成功保存 | 保存当前工作状态、最后一次有效评估快照及下一节点；恢复时跳过已完成节点，不从头执行 |
| 工具调用已完成且结果成功保存 | 复用原查询记录和证据，不重新调用工具 |
| 工具调用期间进程中断 | 不自动重发；保留已保存结果，对无法确认结果的调用记录“执行中断，结果未知”，不作为假设反证 |
| 核心模型调用期间中断且未保存有效输出 | 不自动重新调用；按核心执行异常收尾，使用已有有效快照或已采集事实生成程序兜底报告 |
| 报告生成期间中断 | 已保存报告直接复用；未保存报告使用程序兜底，不重新请求报告模型 |
| 恢复时已超过阶段或总截止时间 | 仅执行当前阶段允许的操作；总截止后只做程序收尾、持久化及事件补交付，不发起新的模型或工具调用 |

工具中断后能否继续调查，仍根据已有证据、替代路径和剩余预算判断，不自动判定整次调查失败。无可恢复业务结果的中断调用以 `failed` 及明确的 `status_reason` 保存，不伪造正常证据，也不新增查询业务状态。部分已保存数据继续遵守完整结果和部分返回规则。

恢复必须同时具备以下保护：

1. 原始截止时间、已用轮数、工具调用计数、内部往返计数及当前节点输出修正次数均持久化，不因恢复重置。首次开始后的重启及恢复等待时间消耗原有时间窗口，不属于执行前排队。
2. 查询终态与对应证据一起提交；节点有效更新、相应有效评估快照及下一节点一起提交。未经成功提交的模型输出不算有效更新，不能留下半份判断。
3. 报告保存和终止事件补交付具有幂等性，恢复不产生重复报告、重复查询记录或重复终止记录。
4. 复用现有租约，并在状态写入时校验当前执行者仍持有有效租约，防止新旧 worker 同时推进同一任务；仅定期续租不足以保证该边界。

**已确认的崩溃窗口取舍：** 调用前先持久化预算占用，再发起请求。正常执行仍按实际发起计工具次数，并在本批首个实际调用发起时计轮；若进程恰好在持久化与请求发起之间中断，恢复无法确定是否已经发起，该调用及相关首批轮数的预算占用不返还，明确标记“发起状态不确定”。可明确证明尚未发起的其他计划不占用实际调用预算。此异常规则避免恢复后重复查询或超预算，但可能少用一次调用额度；不能将不确定占用声称为已确认实际调用。

执行中状态、预算预占及不确定标记属于任务执行层内部信息，不写入执行后查询记录来冒充已执行事实，不扩展已确定的五类业务数据字段。恢复不保证远端调用已经取消，也不保证每次故障都能无损续跑。后续测试必须覆盖安全节点恢复、已保存结果复用、调用发起不确定、预算与截止时间不重置、租约失效写入拒绝及报告/事件幂等交付。

#### 异常报告与任务终态

报告依据按以下顺序选取：

1. 有成功的最终评估时，使用其完整有效结果。
2. 最终评估失败但有有效历史快照时，使用快照表达此前判断，单独说明未评估的新证据和假设修改，不混用新旧内容。
3. 从未形成有效评估时，只报告已采集事实、执行情况及“尚未形成有效根因判断”，不拼凑诊断结论。

正常调查完成但根因 `unconfirmed`，不因此认定执行失败。核心模型失败导致诊断不能继续时，保留任务执行异常，不能因交付兜底报告就伪装成正常调查完成。只有报告模型失败时，保留有效诊断结论并交付程序报告，记录报告生成异常；报告失败不反过来改写根因。

纯执行异常不等于 `critical_data_unavailable` 或 `budget_exhausted`。没有适用诊断停止原因时，允许结束对象的 `stop_reason = null`，通过任务错误及 `explanation` 说明；有真实预算耗尽等事实时，才使用相应原因。**`null` 不再只表示调查仍在运行，下游必须结合任务终态判断。** 用户已确认以下终态及诊断 SSE 映射，不另造任务状态枚举。

#### 已确认的统一终态与诊断 SSE

用户经整体审阅后确认：由同一个程序收尾流程生成终态，一致更新诊断任务、后台 job 和终止事件，不由不同层分别判断成功或失败。

| 结束情况 | 诊断任务与后台 job 的一致终态 |
|---|---|
| 有效确认具体根因 | `succeeded`，诊断停止原因为 `root_cause_confirmed` |
| 正常达到预算或确认关键数据不可用 | `succeeded`，根因允许未确认，保留相应真实停止原因 |
| 核心模型失败、修正后仍非法或诊断初始化未完成 | `failed`；没有真实适用停止原因时为 `null`，保留错误及程序兜底报告 |
| 只有报告模型失败且程序报告成功保存 | 不改变已确定的诊断终态，记录报告生成异常 |
| 用户取消 | `cancelled`；停止新调用，保留已有数据，程序生成取消说明，不再请求模型 |
| 持久化失败或外层保护超时 | 不宣布成功，按执行异常处理，在存储恢复可用后补齐终态 |

因阶段截止而停止最后评估，按时间预算收尾，注明尚未分析内容；模型在阶段仍有时间时发生接口错误或自身超时，按核心执行异常处理，不一概包装成预算耗尽。8 分钟后只允许程序收尾、持久化及事件交付，不延长模型或工具执行时间。无法正常保存终态时不伪称落盘成功；具体外层保护时间与恢复补交付实现须满足固定截止时间及上述区别。

诊断 SSE 的已确认顺序与消费规则：

1. 报告、诊断任务终态、后台 job 终态和待交付终止事件一致提交，成功提交后再交付前端。存储失败时不能先发成功事件。
2. 有报告时先发 `report`；执行失败时再发 `error`；随后发终态 `task.status`，最后持久化并交付一次 `complete`。
3. 诊断 `complete` 表示本次流已结束，不代表成功；前端根据最终任务状态判断成功、失败或取消，不能凭收到报告或 `complete` 判成功。
4. 单次工具失败使用工具失败事件，不使用终止级 `error` 提前终止整次调查。
5. 重连读取已持久化事件，前端按事件 ID 去重，避免重复显示报告或错误；重复交付不产生新的终止记录。

以上调整仅针对诊断流，同步共享契约、后端与前端消费及合同测试，不改变聊天流语义。后续测试须覆盖正常未确认仍成功、核心执行失败仍可交付兜底、报告单独失败、取消、阶段截止、持久化失败及重连事件去重。

时间阶段、单次超时及程序兜底沿用第 8.2 节，不自动延长预算。正常报告及兜底的内容规则如下；具体输出 schema、持久化和前端交付格式仍需工程对齐。

#### 报告生成分工与内容

**正常报告由程序固定权威结论头部，LLM 组织解释正文，失败时程序生成简短兜底报告。** 这是本次确认的目标方案，不代表现有 Report 已实现；不新增一套复杂的报告业务模型，也不复制一份独立的事故级根因判断。

| 部分 | 生成方式与边界 |
|---|---|
| 是否确认根因、已确认的 `root_cause`、停止原因及任务异常提示 | 程序直接依据选定的有效诊断状态呈现，不交给模型自由改写 |
| 因果过程说明、证据解读、主要调查方向及后续建议 | LLM 根据有效分析组织表达，不首次判定因果、排除竞争解释或确认根因 |

`root_cause = null` 时，头部明确显示“具体根因尚未确认”，不得改成“基本可以确定”。从未形成有效评估时，应更明确说明“尚未形成有效根因判断”。使用历史快照时显式标注“此前有效判断，后续新增内容未完成评估”，不能包装成覆盖最新全部证据的最终判断。

报告采用以下四部分，不要求固定篇幅或将每个假设等长展开：

| 部分 | 内容 |
|---|---|
| 诊断结论 | 具体根因是否确认及已确认的根因内容；未确认时明确说明 |
| 原因与证据 | 已有分析支持的因果过程、整份证据 ID 引用及证明边界 |
| 调查结果与局限 | 主要假设判断、未决问题、未分析内容及停止原因 |
| 后续建议 | 优先补充的信息，以及可考虑的缓解措施、适用前提和风险 |

LLM 可以归纳和安排叙述顺序，但已有分析未形成清楚的因果链时只能说明缺口，不能自行补齐。完整假设状态保留并可查，正文可以突出重要方向，但不能省略影响结论的主要竞争解释或关键反证。程序固定头部不自动保证正文语义正确，正文仍须遵守已有结论和异常校验规则。

证据仅使用整份结果引用，例如“E2 显示连接等待增加，支持连接获取受阻，但不能单独证明连接池上限变化”。不引入条目级 ID，不要求将全部原始结果复制进报告；完整结果继续保存在共享证据集合中。

#### 报告输入与建议边界

Report 获得选定的有效评估及完整假设、关系，关联的完整证据和必要查询上下文，未满足需求、停止事实和执行异常，以及明确标识的未评估新证据和假设修改。未评估内容仅用于说明局限，不授权 Report 接替失败的评估节点进行诊断。保持不压缩 Mock 原始日志、不静默截断的前提，报告本身可以简洁，不逐条复述所有查询。

允许两类后续建议：

- **补充调查建议：** 优先从已有 `gaps` 和 `unmet_requests` 整理，例如补充实际生效配置以验证上限是否变化，保持信息需求可追溯。
- **条件性缓解建议：** 结合有效诊断判断和项目知识，说明适用前提、必要核实及风险。例如“若确认连接池上限低于预期，可由负责人评估恢复原配置，调整前需确认数据库可承载连接数”，不能无条件建议立即扩容。

不能借建议首次引入“连接泄漏”等无证据的新根因；新原因解释属于诊断节点职责。所有处置只是建议，不自动执行，缺少项目信息时不编造命令、配置数值或安全保证。

#### 程序兜底的最小内容

程序兜底不尝试生成完整因果叙事，最少呈现有效结论（没有则明确尚未形成有效判断）、已有假设状态与判断理由、关键缺口和未评估内容、实际停止或异常原因。结论依据仍遵循本节的有效评估与历史快照规则，不能将旧状态移植到修改后的假设上。

例如，历史评估支持连接池容量不足，而“发布降低连接池上限”的细化尚未完成重评时，兜底说明：

> 具体根因尚未确认。此前评估支持连接池容量不足，但“发布降低连接池上限”的细化解释未完成评估。当前缺少实际生效配置的验证，最终评估调用超时。以下判断来自此前有效评估，不包含后续未分析证据。

若只有报告模型失败而诊断已有效确认根因，兜底仍展示该根因，不降级为未确认。兜底不再调用模型修正，也不自动延长时间预算。

复用现有步骤与报告 payload、适配业务数据并同步前端及证据契约的原则已确认，具体接口由工程规格落实，不建设大型新系统。用户确认本期不扩展案例沉淀，新闭环不自动写入案例库或知识库，见第 8.6 节；历史案例及独立功能保留。不把未确认的模型结论写成已验证知识或模板，现有耦合须按该边界最小兼容，不擅自删除现有功能。

- 项目知识少量直接注入是明确前提，不默认新增检索/裁剪基础设施。
- 旧五节点草案已由第 8 节的新分工替代；首轮先采证再生成假设、批内独立查询并行已确认。每轮四次动作、模板最多三个等不作为既定要求；预置模板不是必要依赖，本期不合并假设。旧的独立生命周期方案已由单字段六值方案替代，整体收尾规则见第 5.5 节。

## 10. 多会话协作建议

用户希望避免单会话过长，通过文档传递信息，专题讨论后由统筹会话整合并生成代码。

此前建议的分工为：

| 会话 | 范围 |
|---|---|
| 统筹 | 维护确认原则、协调冲突、整合方案、统一代码实现 |
| 假设与知识专题 | 模板、项目知识、假设生成更新和上下文 |
| 调查与判断专题 | 验证计划、因果判断、预算和停止 |
| 工程落地专题 | 图状态、持久化、报告、契约和测试 |

曾建议后续拆成三个公共文档和三个专题文档：`00-context.md`、`01-design.md`、`02-status.md`，以及 `topics/hypotheses.md`、`topics/investigation.md`、`topics/implementation.md`。

**本次用户只要求一份汇总文档，因此没有创建该六文件体系。** 本文可作为未来拆分的来源。

建议专题阶段不修改公共代码，各会话只更新自己的文档，由统筹会话整合。文件写入才算交接完成，新会话必须实际读取文件，不能假设跨会话共享记忆。

## 11. 新会话接续清单
